## v1 暴露的设计缺口

1. **解释的支持校验与发布权限混在一起。** PM-01/04 已检索到必要事实，初稿却携带阶段序号和来源修订号，先触发数值校验；修复后的模型核验又把“候选、尚未批准”当成事实不受来源支持，或否定附带版本措辞，导致整段被丢弃。应分别处理事实语义、来源元信息与发布资格；不得通过放松正式审核门槛解决。
2. **输入来源校验缺中文等价表达。** PM-06 的真实“果酱”请求被要求改为英文 Jelly；PM-11 的“春27日”不在季节词汇“春季/春天”的匹配范围，实际确实导致多次拒绝及无谓追问。这是合法输入被误拒，不是用户没有提供必要条件。
3. **视觉候选缺少可交付的回答路径。** PM-09 的候选、距离及确认要求存在于工具结果，但未进入可用的最终回答。应允许展示未确认候选和适当的确认步骤，同时继续禁止模型伪造用户确认。
4. **澄清语句本身也会犯错。** PM-12 证明 `NEEDS_INPUT` 状态不能替代语义核对；缺输入时仍可能承诺默认数量/品质/职业。PM-08 也没有充分说明排产能力边界。后续修复应针对通用澄清行为，不能针对题号或把原题改容易。

## 对照与预算的解释边界

初检限制的是整个 `canonical(model_payload)` 的 6000 个 Unicode 字符，包含选中事实/关系、条件、实体、完整来源引文、图片引用及精简封装；不是只统计主记录，也不是总对话上下文上限。完整签名 bundle 与审计 trace 留在服务端。显式补查按批次计量；所有工具输出另计累计字符代理，包含取证、计算和能力发现，不能换算成真实 token 或费用。

比较须实际核对代码哈希、模型网址/名称、快照、协议与样本集合、预算定义哈希；发生代码/配置变化、隐藏初检事实或预算回执不符时，不作公平结论。产品基线直接对原始 Wiki 段落和图像推理，没有图遍历或确定性计算器；不能以缺计算凭据判它数值错误，也不能假装工作流能力相同。

v1 [运行总记录](../../artifacts/v3/post_midterm/evaluation/final-D-all12/run.json)显示代码哈希 `8bbb60e544aee43b4b14b30bded6987d48e2433526eb3291c36d5336821ba1ef`，运行前后无代码/模型变化，预算违例为 0；实际使用 `ecnu-max`/`ecnu-plus`。18 个初检/补查证据块的最大可见长度为 5990 字符；全部工具输出累计字符代理为 192087。后者包含工具元数据，不能当作去重知识量、真实 token、费用或总模型上下文。

结构子集 PM-01/11 均没有图片，BQ/D 会使用 `NO_QUERY_PIXELS` 退化路径；本轮不能证明视觉重排或图片优势。动态 Agent 的实际检索问句与工具轨迹也可能不同，加上单次运行和已暴露开发样例，只能形成候选诊断，不能据此断言图结构稳定优于平面检索。正式独立样例、视觉优势、人工审核与完整产品验收仍待完成。

v1 没有据此完成控制实验，不报告方法排名。v2 已保持问题、图片及期望不变并单独记分。当前可确认的是工程约束拦截了部分错误输入／旧状态，几条实际用户路径已经恢复，同时真实路径仍有误拒、解释撤回及澄清质量问题。
